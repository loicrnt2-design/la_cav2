# La CAV’ — prototype v2

Ouvrir `index.html` dans un navigateur récent : aucun serveur, aucune installation et aucun Node.js ne sont nécessaires. Garder le dossier `assets` à côté des fichiers HTML, CSS et JavaScript.

Le catalogue initial, les prix et les descriptions sont fictifs ; les photos sont des illustrations et ne représentent pas des annonces réelles. Recherche, filtres, fiches et favoris sont interactifs. Les favoris sont conservés dans le navigateur lorsque son stockage local est disponible. Le lien **Admin** ouvre un back-office pour gérer les articles, collections et profils ; les articles publiés alimentent la vitrine. Le mode local est une démonstration non sécurisée : ne pas y saisir de données personnelles réelles. Les messages, achats, paiements, enchères et livraisons ne sont pas connectés. Ce prototype ne constitue pas un site prêt à être mis en production.

## Utilisation locale

Ouvrir `index.html`, puis **Admin**. Les modifications restent dans le stockage local du navigateur ; elles ne sont ni partagées ni sauvegardées dans un serveur. Selon le navigateur, le stockage des pages ouvertes en `file://` peut être isolé ou désactivé : si la vitrine ne retrouve pas les modifications, utiliser un hébergement statique local ou HTTPS, sans Node.js. Ne pas effacer les données du navigateur si vous souhaitez conserver les données locales. L’administration locale n’a pas de mot de passe et n’offre aucune protection.

Dans **Articles**, créer, modifier, publier, archiver et supprimer des fiches ; l’image est une URL HTTPS ou le chemin d’un fichier déjà présent dans `assets/images`. Il n’y a pas d’envoi de fichier ni de stockage d’image. Une collection utilisée par un article ne peut pas être renommée ou supprimée avant déplacement des articles. **Clients** permet de créer des profils de démonstration locaux : ils ne permettent pas de se connecter.

## Configuration Firebase (facultative, Internet nécessaire)

Le SDK Web est chargé depuis le CDN officiel de Google. Créer un projet de **test** Firebase, enregistrer une application Web, activer Authentication par e-mail/mot de passe et créer une base Cloud Firestore. Ces opérations sont manuelles dans la console Firebase et peuvent occasionner des coûts suivant l’usage. Pour les connexions réelles, utiliser de préférence un hébergement HTTPS et configurer les domaines autorisés ; l’ouverture `file://` et certaines restrictions de clé peuvent ne pas être compatibles avec Firebase selon le navigateur.

1. Dans Firebase Authentication, créer un utilisateur de test administrateur et noter son **UID**.
2. Dans la console Firestore, copier les règles de `firestore.rules`, remplacer `REMPLACER_PAR_UID_ADMIN` par cet UID, puis **publier**. La valeur de remplacement par défaut refuse toute administration. Vérifier les règles avec l’émulateur ou le simulateur de règles avant utilisation.
3. Renseigner les quatre valeurs de configuration Web (`apiKey`, `authDomain`, `projectId`, `appId`) dans l’onglet **Admin → Firebase**, ou dans `firebase-config.js` avant de partager le site. Une configuration enregistrée dans le navigateur prend priorité sur le fichier. Pour la retirer, utiliser **Effacer la configuration du navigateur** ; une configuration complète encore présente dans `firebase-config.js` restera active et devra également être vidée pour revenir au mode local.
4. Se connecter dans **Admin → Firebase** avec l’utilisateur administrateur créé. La clé API Web est publique et identifie le projet ; elle ne donne pas les droits admin. Ne jamais placer de clé privée, compte de service ou mot de passe dans le code. Restreindre la clé API conformément aux recommandations Google.
5. Cliquer sur **Initialiser les collections**. Cette opération crée uniquement les documents `_schema` de `products`, `categories` et `customers`, sans écraser un document existant. Firestore crée ces collections à la première écriture. Elle ne crée ni la base ni les règles, et ne crée aucun client ni article. Créer ensuite une collection, puis un article publié dans le back-office.
6. La vitrine lit les articles publiés et les collections de Firestore. Les données locales ne sont ni importées automatiquement ni supprimées. En cas d’erreur Firestore, aucune donnée locale n’est substituée silencieusement.

Les clients peuvent s’inscrire et se connecter depuis **Mon compte** lorsque Firebase est configuré. Un profil Firestore est associé à leur UID ; ils peuvent modifier leur nom. Les règles proposées limitent les profils à leur propriétaire et à l’UID administrateur. Si la création du profil échoue après création du compte Authentication, le client peut se connecter et enregistrer son nom pour réessayer.

Dans le back-office Firebase, la suppression d’un profil ne supprime **pas** son compte Authentication ; cette opération, ainsi que la modification d’identifiants, reste à effectuer dans la console Firebase ou un futur serveur sécurisé. Il n’existe pas ici de désactivation effective d’un compte, d’export, de récupération de mot de passe, de vérification d’adresse e-mail, d’administration multi-utilisateur, de gestion d’images ou de procédure de suppression complète. La même session Firebase est partagée entre les pages d’une même origine. Ne pas utiliser de données réelles tant que la sécurité, les droits et les parcours ne sont pas validés. Firebase n’a pas été configuré ni testé contre un projet réel dans ce prototype.

Documentation officielle : [configuration Web](https://firebase.google.com/docs/web/alt-setup), [Authentication](https://firebase.google.com/docs/auth/web/password-auth), [règles Firestore](https://firebase.google.com/docs/firestore/security/get-started), [clés API Firebase](https://firebase.google.com/docs/projects/api-keys).
